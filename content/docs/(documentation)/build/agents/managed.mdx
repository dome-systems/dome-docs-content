Run managed agents in Dome without operating a worker. Configure their prompt, model, gateway, and triggers, then start runs manually, on a schedule, or through signed webhooks.

## Overview

A managed agent is one of Dome's three agent types. Dome runs its execution worker; an external agent runs in your own runtime, and an interactive agent represents signed-in human gateway traffic. A managed agent's configuration has four parts:

| You configure | Dome uses it for |
| --- | --- |
| System prompt | Persistent instructions for each run |
| model or pool | The model the worker invokes |
| gateway | The models and tools the worker can reach |
| [Triggers](/build/triggers) | When Dome starts a run |

The managed agent keeps its ordinary identity, gateway grant, rules, lifecycle, and audit behavior. Dome holds the runner credential; it is never returned to you.

The typical workflow is:

1. [Register the agent](#register-agent) with its prompt, model, and gateway.
2. Choose how to start work:
   - [Run the agent directly](#run-managed-agent) for an ad hoc task, test, or debugging session.
   - Create a [schedule](/build/triggers#create-schedule) or [signed webhook](/build/triggers#create-signed-webhook) when work should start automatically. [Fire a trigger](/build/triggers#fire-a-trigger) on demand.
3. [Inspect runs](#inspect-managed-agent-run) and adjust the configuration when needed.
4. [Manage the lifecycle](#manage-lifecycle) when the worker must stop everywhere.

## Requirements

Before you begin:

- Ask an organization owner or administrator to [enable public preview](/manage/public-preview) for the organization.
- Authenticate the Dome CLI and select a workspace.
- Create a [gateway](/build/gateways) that admits the managed agent and contains its model and tools.
- Select a model or pool available through that gateway.

### Permissions

Managed agent and trigger operations require platform permissions. Each operation states its required permission inline.

| Permission | Grants |
| --- | --- |
| `managedagents.view` | List managed agents and inspect run history |
| `managedagents.manage` | Create, update, delete, and configure managed agents and triggers |
| `managedagents.invoke` | Start manual runs and fire triggers |
| `agents.register` | Create the underlying agent and update its shared settings |
| `agents.suspend` | Suspend or reactivate the underlying agent |
| `agents.revoke` | Revoke the underlying agent |
| `rules.deploy` | Change the managed agent's gateway grant |

## Register agent

Create a managed agent with a name, system prompt, model or pool, and gateway. Dome keeps the runner key and never exposes it.

<Callout icon="key">Requires `managedagents.manage`, `agents.register`, and `rules.deploy`.</Callout>

<Tabs items={["CLI", "MCP", "API", "Agent"]}>
  <Tab value="CLI">
    ```bash
    dome managed-agents create \
      --name nightly-triage \
      --system-prompt "Triage issues filed since the last run." \
      --model openai-prod \
      --gateway production
    ```

    Each managed agent runs through exactly one gateway. The gateway grant permits every tool the gateway exposes, so Dome rejects separate tool grants on the managed agent.

    <Callout icon="terminal">Reference: [`dome managed-agents create`](/docs/cli/build/managed-agents#create-managed-agent)</Callout>
  </Tab>

  <Tab value="MCP">
    Tool: `dome_managed_agents_create`

    ```json
    {
      "name": "nightly-triage",
      "system_prompt": "Triage issues filed since the last run.",
      "model": "openai-prod",
      "gateway": "production"
    }
    ```

    <Callout icon="cpu">Reference: [`dome_managed_agents_create`](/docs/reference/mcp/managed-agents)</Callout>
  </Tab>

  <Tab value="API">
    ```http
    POST /v1/managed-agents
    Content-Type: application/json

    {
      "agent": {
        "workspace_id": "{{WORKSPACE_ID}}",
        "name": "nightly-triage",
        "allowed_gateway_ids": ["production"]
      },
      "system_prompt": "Triage issues filed since the last run.",
      "default_model": "openai-prod"
    }
    ```

    <Callout icon="code">Reference: [`CreateManagedAgent`](/docs/api/tag/managed-agents/create-managed-agent)</Callout>
  </Tab>

  <Tab value="Agent">
    ```text title="Create a managed agent"
    Create a managed agent named "nightly-triage". Use the "openai-prod" model through the "production" gateway, with the system prompt: "Triage issues filed since the last run."
    ```
  </Tab>
</Tabs>

Use `dome managed-agents get nightly-triage` to inspect the system prompt, model, gateway, and attached triggers. Use `dome managed-agents update nightly-triage` with `--system-prompt`, `--model`, or `--gateway` to change the managed agent configuration.

### Create from a file

Use a JSON or YAML definition when you want a reviewable managed agent configuration, such as in CI. The file has the same fields as the [Create managed agent API request](/docs/api/tag/managed-agents/create-managed-agent). The `agent` object is the underlying agent registration; it contains the name and its one gateway grant.

```yaml managed-agent.yaml
agent:
  name: nightly-triage
  allowed_gateway_ids: [production]
system_prompt: Triage issues filed since the last run.
default_model: openai-prod
```

```bash
dome managed-agents create --file managed-agent.yaml
```

<Callout icon="terminal">Reference: [`dome managed-agents create --file`](/docs/cli/build/managed-agents#create-managed-agent)</Callout>

## Rotate runner key

<Callout icon="key">Requires `managedagents.manage`.</Callout>

### Control run behavior

Manual runs are enabled by default. Turn them off when an agent should start only from its schedules and webhooks:

```bash
dome managed-agents update nightly-triage --manual-runs=false
```

This refuses **Run now** and `dome managed-agents run`, but does not pause a schedule or webhook. To stop every new run, [suspend the underlying agent](#suspend).

Bound each run with `--turn-timeout`, `--on-turn-timeout`, `--max-turns`, and `--max-run-duration`:

```bash
dome managed-agents update nightly-triage \
  --turn-timeout 5m \
  --on-turn-timeout retry \
  --max-turns 100 \
  --max-run-duration 1h
```

The platform defaults are a 5-minute turn timeout, 50 turns, and a 1-hour run duration. Use a [per-run quota](/govern/quotas#limit-one-managed-agents-run) to limit token use or estimated provider spend. Run limits do not set a token or cost budget. On update, set a numeric limit to `0`, or use `--on-turn-timeout default`, to return that setting to the platform default.

A run moves from `pending` to `running`, then ends as `succeeded`, `failed`, or `cancelled`. Dome can retry an infrastructure failure, but it does not retry a run that reached the model.

### Use run variables

In an agent's system prompt, a manual-run input, or a trigger's configured input, reference values that Dome fills when the run starts:

| Variable | Value |
| --- | --- |
| `{{dome.now}}` | Run start time in UTC |
| `{{dome.today}}` | Run date in the trigger's time zone |
| `{{dome.timezone}}` | Schedule trigger time zone, or `UTC` otherwise |
| `{{dome.scheduled_for}}` | When the run was due or queued, in UTC |
| `{{dome.last_successful_run}}` | Start of the agent's last successful run, or `none` |
| `{{dome.run_id}}` | Current run ID |
| `{{dome.agent.name}}` | Managed agent name |
| `{{dome.trigger.name}}` | Trigger name, or `none` for a manual run |
| `{{dome.source}}` | `schedule`, `webhook`, or `manual` |

For example, `Review changes since {{dome.last_successful_run}}.` is filled in at the start of each run. Dome leaves an unknown `{{dome.*}}` reference unchanged. A webhook request body is passed to the run as sent, so run variables in the body are not substituted.
